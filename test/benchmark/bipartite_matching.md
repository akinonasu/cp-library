# 二部マッチング

2026-10-20。`graph/matching/bipartite_matching.hpp` を追加した。共有する探索・解析を `components/bipartite_matching_core.hpp` に置いた。実装は標準 C++ で、固定長の配列や x86 専用命令は使わない。

## 参考提出

Library Checker の [Matching on Bipartite Graph](https://judge.yosupo.jp/problem/bipartitematching) について、公開 API の `status=AC&order=+time&limit=20` を取得した。取得した一覧・時刻・ソースの SHA-256 は `results/bipartite_matching/references.json`。

| 提出 | 取得時の最大時間 | 確認した実装 |
| --- | ---: | --- |
| [396318](https://judge.yosupo.jp/submission/396318) | 70 ms | 双方向 CSR、距離ラベル、未対応右頂点のキュー、周期的な全体 BFS。固定配列と blazingio |
| [396316](https://judge.yosupo.jp/submission/396316) | 71 ms | 同じ距離ラベルの方式。動的な配列を利用 |
| [396312](https://judge.yosupo.jp/submission/396312) | 72 ms | 色配列で左右を指定する距離ラベルの方式 |
| [339108](https://judge.yosupo.jp/submission/339108) | 75 ms | 汎用 CSR と色配列を使う距離ラベルの方式 |

これらはコード内で Hopcroft–Karp と名付けられているが、通常の BFS と増加道 DFS を交互に行う実装ではなく、距離ラベルを更新しながら未対応頂点を移す方式だった。今回の実装では、その方式を作業量制限付きの初期解改善に使い、残りを通常の Hopcroft–Karp で解く。公開ジャッジ時間と以下のローカル時間は直接比較しない。

## 実装

- 辺追加時に、両端が未対応なら貪欲に対応付ける。ただし全ての入力辺を保存し、後の被覆・辺の分類にも利用する。
- 小さい側を探索元として片方向 CSR を作る。左右の頂点番号・辺 ID は公開 API では変えない。
- 隣接辺を持つ未対応の探索元が `max(64,小さい側の頂点数/32)` 以下なら、通常の Hopcroft–Karp を先に最大8段階行う。
- 残った場合は、距離ラベルによる初期解改善を行う。全体 BFS・隣接辺走査・キュー処理を数え、`16*(N+M)` を超える前に打ち切る。途中でも有効なマッチングを維持する。
- 最後は Hopcroft–Karp で最大性を確認する。小さい側の全頂点を対応付けた場合は、それ以上の探索を省略する。
- 増加道 DFS・強連結成分分解は明示的なスタックを使う。

このため、初期解改善の作業は $$O(N+M)$$ に制限され、全体の最悪計算量は $$O((N+M)\sqrt K)$$、空間は $$O(N+M)$$。$$K$$ は小さい側の頂点数。入力名・乱数 seed・頂点番号の特定パターンによる分岐は使わない。

## 便利機能

最小頂点被覆・最大独立集合・最小辺被覆・左右の Hall 条件の反例・採用辺 ID・各辺の分類を追加した。

解析用の交互グラフでは、採用した辺 ID だけを右から左、他の辺を左から右へ向ける。未対応の左からの到達、未対応の右への到達、強連結成分を使い、各辺が最大マッチングに含まれない・任意・必須のいずれかを判定する。多重辺の別 ID も扱う。

解析は必要な機能を呼んだときだけ作り、辺追加まで再利用する。最大マッチングだけの計算では解析グラフや SCC を作らない。辺追加後の再計算は既存の有効なマッチングを利用するが、全操作列に対する動的計算量は保証しない。

## 試した変更

`screen_warm_initial.json`・`screen_hybrid_phases.json`・`screen_hybrid_distance.json`・`screen.json` に初期比較を残した。

| 候補 | 結果 |
| --- | --- |
| 通常の Hopcroft–Karp のみ | 難しい増加道の分布では約0.5秒になった |
| 距離ラベルの前処理を常に行う | 難しいケースは改善したが、疎グラフでは確保・走査が余分になった |
| 全グラフで先に2段階の HK | 一部の疎グラフを改善したが、難しいケースにも数msを追加した |
| 短い増加道を距離で制限 | 小さいランダム入力には有効だが、難しいケースの前処理が増えた |
| 未対応頂点数で方式を選択 | 小さいランダム入力の速度を維持し、難しいケースを改善した |
| 前処理上限を4倍に縮小 | 一部の難しいケースが途中で打ち切られ、HK の負担が残ったため不採用 |
| 前処理上限を64倍に拡大 | 16倍から一貫した改善が得られず不採用 |
| 小さい側への交換・貪欲初期化を無効化 | 不均衡なグラフや一部のランダム入力で悪化したため不採用 |

未対応頂点が少ないときに HK を無制限に使う初期案は、`unique_matching_04` で約96.5 msだった。最大8段階に制限した最終版は23.6 msとなった。初期案の全ケース結果は `measurements_initial.json`。初期案と最終版ではソースと測定時点が異なるため、厳密な同時比較とは扱わない。

## 測定条件

WSL2 / Linux x86_64、Intel Core i7-13700F、GCC 15.2.0、CPU 2。`-std=c++23 -O2 -DNDEBUG -march=native -ftrivial-auto-var-init=zero`。コンパイル・他のテストと測定を同時に行わず、ウォームアップ1回、固定 seed で各ラウンドの実行順をシャッフルし、7回測定した。公式生成器の44ケースと独自8分布を使う。公式データの commit・入力のハッシュ・全試行は `measurements.json`。

API の測定は、入力を共通の配列へ読み込んだ後から開始する。今回の実装はオブジェクト構築・辺追加・CSR 構築・探索・オブジェクト破棄を含む。通常 HK 版は同じクラスと部品から初期解改善だけを除いたもの。参考提出は、元の距離ラベルの関数と固定配列を取り出し、双方向 CSR 構築・初期化・探索を測る。参考提出の固定配列は静的領域なので、その確保・破棄は時間外である。

参考提出の実行ファイル自体も変更せずにコンパイルし、プログラム全体の時間を別に測る。今回の提出コードは FastInput/FastOutput、参考提出は元の blazingio を使う。したがって全体時間の比較はアルゴリズム単体の比較ではない。

全体時間にはプロセス起動・入出力・終了を含む。公式の入力は Linux 側のキャッシュ、独自入力と出力は `/mnt/c` の作業領域に置いた。同じ入力では全方式が同じファイルを使う。特に独自ケースの全体時間には WSL のファイル操作の影響もある。ケースの分布間で、全体時間の差をアルゴリズムだけの差とは解釈しない。

非負整数の一括入出力も試したが、このドライバーでは通常の Fast I/O より遅かったため採用しなかった。例えば `many_paths_00` は28.3 msから33.2 ms、`unique_matching_00` は51.9 msから56.0 msだった。`full_bulk_ms` に試行を残し、採用した通常版の値を `full_ms` に保存する。アルゴリズム部分は変更せず、入出力を含む測定だけを追加した。通常版へ戻したソースは最初の全体測定時の SHA-256 と一致することを確認した。

独自8分布は、長さ100000の増加道、100000対1000とその転置、700対700の密グラフ、辺なし、1頂点への集中、多重辺、独立した2対2の成分。生成規則は測定スクリプトに置く。

AtCoder / Library Checker 実機への今回のオンライン提出は行っていない。最速を達成したとは主張しない。上表のとおり、通常 HK や参考提出より遅い分布もある。

## 検証

- 左右0〜4頂点、辺候補12本以下の全9427グラフ。全マッチングを列挙し、最大本数と各辺の採用頻度を照合。
- 左右0〜7頂点のランダムな多重グラフ500ケース。各辺追加後に再計算・解析し、キャッシュの無効化も確認。
- 前処理の上限0・1・16倍で、途中のマッチングが有効であることと、残りを HK で解いた結果を全列挙と比較。
- 最小頂点被覆・最大独立集合のサイズと各辺の被覆、最小辺被覆のサイズ・孤立頂点・空グラフ、左右の Hall 条件の反例の隣接集合を確認。
- 左右200000頂点の長い増加道と、200000対1のグラフ。再帰スタックに依存しないことを確認。
- GCC・Clang のユニットテスト、Clang ASan/UBSan、両コンパイラで公式44ケースの公式チェッカー検証。
- ヘッダー2個と提出コードの Bundle、説明例のコンパイル・実行。GCC では AtCoder の constexpr 制限でも構文検査。
- native の全測定では公式44ケース・独自8ケースの全出力を公式チェッカーで検証し、API の全試行で本数も照合。

ソースと結果は `validation.json`・各ログに保存する。Mac 実機での速度は測定していない。
