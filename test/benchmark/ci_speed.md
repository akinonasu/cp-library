# CI の高速化

[参考リポジトリのワークフロー](https://github.com/kemuniku/cplib/blob/main/.github/workflows/verify.yml)は、テストデータをキャッシュし、検証結果を再利用しています。こちらでは GCC・Clang・sanitizer・ヘッダー単体・Bundle の検証を維持し、データの復元範囲と通過結果の保存単位を変更しました。

## 調査した実行

[従来の実行](https://github.com/qandori/cp-library/actions/runs/39148705406)では、122本のジャッジ検証が再実行され、その工程が1,327秒、データキャッシュの復元が144秒、保存が177秒でした。[別の実行](https://github.com/qandori/cp-library/actions/runs/39154854028)でも復元に189秒、直近の実行では197秒かかっていました。キャッシュ一覧の圧縮サイズは10,430,699,807バイトでした。

## 変更

- 成功結果を照合して対象を選んだ後、必要な問題のデータだけを復元する。ジャッジ対象がなければ、データの clone・復元・キャッシュクライアントのインストールも省略する。
- GitHub 公式 `@actions/cache` を使い、問題ごとに独立したキャッシュを持つ。同じ問題を使う複数のドライバーでは共有する。
- Library Checker の問題ソース・共通部品・生成スクリプト、コンパイラと Python、依存パッケージ指定が変わるとデータキャッシュも更新する。他の問題の変更では更新しない。
- キャッシュキーと Git の内容一致を確認してからソースの日時を正規化し、clone の日時だけで同じデータを再生成することを防ぐ。
- データは公式 `generate.py` で検証し、入力・正解出力を hard link で共有する。同一ファイルシステムでない場合はコピーする。
- 1本のドライバーが全コンパイラで通るたびに成功結果を保存する。後続の失敗・中断があっても、通過したドライバーを次回再利用する。
- 既存の成功結果のキーを維持し、今回の CI 変更を理由にライブラリ全体を再テストしない。

強制全件検証と、明示的な no-cache 検証では、それぞれ従来どおり対象を実行します。失敗・未完了のテストを成功として保存しません。no-cache 検証にはデータキャッシュを持ち込みません。

## 測定方法

`.github/workflows/ci-speed-benchmark.yml` で `test/auxiliary_tree.test.cpp` と `test/lowest_common_ancestor.test.cpp` を実行します。両方とも Library Checker の LCA を使い、データは1問題分です。各25ケースを GCC・Clang で検証します。初回はデータ生成と保存を含み、2回目は保存済みデータを復元します。2回目には変更のないヘルパーテストを再実行しません。

測定時刻は2026-10-19（日本時間）、Ubuntu 24.04、Python 3.12、GCC・Clangです。測定用ブランチを使い、main のワークフローや公開ページは実行していません。

## 結果

[初回](https://github.com/qandori/cp-library/actions/runs/39162134967)、[復元時の最終版](https://github.com/qandori/cp-library/actions/runs/39162603219)。最終測定のソースは `c6006efbcd5ec47ca8203f47277633903fdf20d7` です。

| 工程 | 初回 | 復元時 |
| --- | ---: | ---: |
| ソース・対象の準備 | 2秒 | 2秒 |
| キャッシュクライアントのインストール | 3秒 | 3秒 |
| 問題データの復元 | 1秒（未登録） | 2秒（ヒット） |
| データ生成・2本の検証 | 40秒 | 25秒 |
| 問題データの保存 | 4秒 | 1秒（登録済み） |

この1問題分の圧縮キャッシュは94,744,211バイトでした。従来の全問題分10.43 GBの復元144–197秒に対し、今回必要な問題だけを復元すると2秒でした。初回は新しい問題単位のキャッシュを作成します。対象問題が増えれば転送量・時間も増えるため、全件検証も常に2秒で復元できるという意味ではありません。

ソースの日時を正規化する前には、キャッシュヒット後にもデータを再生成していました。[その実行](https://github.com/qandori/cp-library/actions/runs/39162298995)は検証工程53秒で、最終版では再生成0回、25秒でした。ホスト間の負荷差もあるため、速度比の一般化はしていません。

CI ヘルパーの135テストが Linux で通過し、追加した日時正規化の5テストも別途通過しました。2本のドライバーそれぞれ25ケースを GCC・Clang で通過し、既存の成功キャッシュの判定値が変わらないことと、失敗・中断後には完了したドライバーだけを再利用することを確認しました。復元処理を正式な JavaScript Action として実行することも実機で確認しています。

最終ソースとの一致を確認し、測定用ブランチと、そのブランチだけの測定用キャッシュは削除しました。
