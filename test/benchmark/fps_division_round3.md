# FPS 除算・線形漸化式の追加測定

基準版は `bd951dce6fdcb3ea9db4fcef342147012a8ab0c0`。2026-10-19 UTC に測定した。Bostan–Mori の NTT 倍長化で、入力コピーと係数倍を変換へ融合する変更を採用した。除数のコピー融合と除算のプラン調整は、以下の理由で採用していない。GCD・多項式逆元の製品差分はない。

## 参照と採用した変更

[Kth term of Linearly Recurrent Sequence 405848](https://judge.yosupo.jp/submission/405848) と [Division of Polynomials 409561](https://judge.yosupo.jp/submission/409561) の編集していない原本を同じ flags で比較した。SHA-256 はそれぞれ `f6d088ba82caad15a517bffc2396f4a1d81dd75ea98ed0992226c4fa0b847ff2`、`fd06ec63bfe326a8f8c2b25292ecf38d77c4fd0114fbaa2565e4c667b8b4eeb1`。

現行の Bostan–Mori は、倍長化のたびに変換済みの前半を後半へコピーし、後半を逆変換してから、もう一度走査して twist と正規化を掛けていた。参照原本は逆変換の最終段と twist を融合しており、この部分が不足していた。

新しい `components/fps_bostan.hpp` では、最初の8要素の逆変換を前半から後半へ直接書くことでコピーを消し、最後の radix-2 / radix-4 と係数倍をまとめる。分母の最高次項の補正は、正規化前の `2*n*leading` から、係数倍の後の `2*leading` へ移した。定数項の twist が `1/n` なので同じ値になる。

対象は Linux x86_64 / GCC で、`NTT::vectorized()` が真、変換長が8以上の場合。AVX2 を使い、AVX512 は必要としない。その他は従来の計算へ切り替える。入力側の変換済み配列、公開 API、汎用型を維持する。SIMD の読み書きは生存中の `NTT::U` の8要素に限り、配列外の padding は追加していない。

## 計測条件

AMD EPYC 9V74 / Linux x86_64 / GCC 14.2.0、CPU 2固定。コンパイル flags は全版で `-std=c++23 -O2 -DEVAL -DONLINE_JUDGE -ftrivial-auto-var-init=zero -march=haswell`。assert は有効。ビルド・検証は `/tmp/cp-fps-tuning.lock` の共有ロック、計時は排他ロックを使った。基準版の Git archive を専用ディレクトリへ復元し、他の並行した変更を混ぜずに測定した。

各入力・各版を1回予備実行し、反復ごとに順序をシャッフルして21回測定した。起動・ファイル入出力・計算・終了を含む wall time の中央値で、単位は ms。checker は計時の後に `checker input actual answer` の順で毎回実行した。paired 差は同じ反復の「基準版−候補」の中央値で、2つの中央値の差とは異なる。勝数は paired 差が正の回数。

## 採用しなかった除算の入力融合

基準版は被除数を直接読む一方、除数は Montgomery ワードを正規化して所有する配列へコピーする。候補は除数も `span<const Mint>` とし、反転や折り畳み、最初の変換の読み込みへ正規化を融合した。コピーと `Arena::footprint(m)` の領域を省くが、計算終了後に出力を追加する順序は維持する。raw `uint32_t` 経路は元のコピーと変換を使う。

## 除算のプラン調査

原本から移植した cost model が現在の CPU でも適切か、各ブロック幅と剰余の計算法を1回予備実行＋9回ずつ比較した。プラン順は seed 20261103 で各反復にシャッフルした。入力と商・剰余のバッファは計時前に確保し、プランごとの arena 確保・計算・解放を含む。各試行の全 raw ワードを現行プランの商・剰余と照合した。これは計算部分の診断で、上の全体時間とは直接比較しない。

| 入力 | 現行のブロック幅 | 剰余 | 実測で最良の幅 | 最良 ms |
| --- | ---: | --- | ---: | ---: |
| v_random_00 | 4096 | wrap | 4096 | 1.503 |
| v_random_01 | 8192 | split | 8192 | 2.798 |
| v_random_02 | 65536 | wrap | 65536 | 5.770 |
| v_random_03 | 65536 | tail | 65536 | 4.408 |
| n_max_00 | 16384 | split | 16384 | 3.652 |

5入力すべてで現行のプランが実測でも最良だった。cost model の定数や閾値は変更していない。

## 検証

- GCC14 の通常 `-Wall -Wextra -Werror` で、新ヘッダー単体、新しい境界テスト、`fps_algorithms.cpp` が成功した。後者は Mint / PlainMint の双方で素朴な漸化式・有理式の係数と比較する。
- 新しい境界テストと `fps_algorithms.cpp` は ASan / UBSan でも成功した。
- GCC13.3.0 で新ヘッダー単体と境界テスト、Clang19.1.7 で新ヘッダー単体と `fps_algorithms.cpp` の通常 Werror が成功した。
- 境界テストは8〜262144要素の各2冪を、配列をページ先頭・末尾に置いて照合する。前後は `PROT_NONE`、入力は読み取り専用。`2p-1` を含む lazy ワードと0を含む係数倍を、従来の逆変換＋係数倍と比較する。
- Kth term of Linearly Recurrent Sequence の公式全20件に成功した。計時中の2試行×396回の公式 checker もすべて成功した。除算候補の計時中の2試行×330回もすべて成功した。

除数融合の不採用候補も、除数前後の guard page・読み取り専用入力・lazy ワード・入出力 vector の共有を含む通常 Werror の除算テストを通過した。[記録](results/fps_division_round3/divisor_check.json) を残した。

検証は同じ固定スナップショットへ採用候補を適用して行い、依存ヘッダーの前後のハッシュが一致した。[検証コマンドと結果](results/fps_division_round3/check.json)、[ログ](results/fps_division_round3/check.log) を保存した。

## 原票と再現

[原票ディレクトリ](results/fps_division_round3/) に、全試行・順序・入力/出力/checker・全依存ヘッダー・ドライバー・原本・バイナリのハッシュ、コンパイルコマンド、候補パッチ、計測と検証のハーネスを保存した。`manifest.json` は原票の SHA-256 一覧。

公式入力と参照原本を用意し、リポジトリのルートで次を実行すると、基準 commit と候補を復元し、記録した全ヘッダーと参照原本のハッシュを確認できる。

```sh
python3 test/benchmark/results/fps_division_round3/replay.py \
  --repository "$PWD" --work /tmp/fps-division-round3-replay-new \
  --official-root /tmp/library-checker-problems --references /tmp/fps-reference \
  --prepare-only
```

この復元・照合は [実行済み](results/fps_division_round3/replay_preparation.json)。`--prepare-only` を省略すると同じ flags で再ビルドし、除数融合と Bostan–Mori の2組の21回測定を行う。この再現ハーネスによる全計時の再実行はしていない。バイナリのハッシュや絶対時間は、コンパイラ・ソースの絶対パス・測定環境で変わり得る。

`--diagnostics` を指定すると、通常の全体測定の代わりにプラン grid と出力バッチ micro を同じ条件で再ビルド・再実行する。診断ハーネスの全再実行はしていない。
