# FPS 一括入出力の比較

2026-10-19（Asia/Tokyo）、Linux x86_64 / AMD EPYC 9V74 / GCC 14.2.0、CPU 2 で測定した。計算部分を同じ現行の対数に固定し、`ce81108` の入出力部品と採用する入出力だけを差し替える。

参照は [409452](https://judge.yosupo.jp/submission/409452) の `BulkParser` と `fields`。4 本の独立したポインタで 2 トークンずつ読み、入力位置の依存を並列化する。ただし最速コードの前後の padding、可変な static 作業領域、上限のない区切り検索は利用しない。

採用版は次を変更した。

- 入力をトークン境界で 4 ストリームに分け、長さ・全桁・uint32 上限を確認してから結合する。
- 区切りの検索は 32 byte 以内に制限する。入力末尾と異常なトークンでは元の位置から通常の読み込みに戻る。
- 呼び出しごとに所有する作業領域を使い、別々の入力の処理で可変バッファを共有しない。
- 32768 値ずつ読み、64 個の生成済み `Mint` へ SIMD で変換して追加する。全体の零初期化と係数ごとの容量判定を省く。
- 出力は Montgomery 解除を 8 値ずつ行い、25600 値のブロックを整形する。大きなブロックは `FastOutput` の未出力部分を先に処理し、余分なバッファへのコピーを省く。部分書き込みとエラーも処理する。

`-std=c++23 -O2 -DEVAL -DONLINE_JUDGE -ftrivial-auto-var-init=zero -march=haswell`、assert 有効。全版のビルド後、排他ロック内で測定する。通常ファイルから公式 `max_random_00.in` を読み、通常ファイルへ出力し、すべての出力を公式 checker で確認する。予備実行 1 回、順番をシャッフルした 11 回の中央値、単位 ms。

| 入出力 | 入力 | 同じ対数計算 | 出力 | プロセス全体 |
| --- | ---: | ---: | ---: | ---: |
| ce81108 の入出力 | 2.840 | 9.562 | 1.722 | 16.296 |
| 採用版 | 1.860 | 9.597 | 1.555 | 15.107 |

入力を約 34.5%、全体を約 7.3% 短縮した。計算部分を同じにした比較であり、FPS 計算全体の変更前後の比較とは区別する。全ヘッダーとドライバー・入力・バイナリのハッシュ、全試行は [記録](results/fps_io_pipeline.json) に残す。

長さ判定を branchless にする案は、同一セッションで入力 1.930 → 1.949 ms となり採用しなかった。作業領域を呼び出し側で 1 回確保して使い回す案も、別セッションで入力 1.792 → 1.858 ms となり採用しなかった。後者は計算部分にも差が出ており、全体の差をメモリ確保だけに帰属させない。候補比較は [長さ判定](results/fps_io_pipeline_candidates.json)、[作業領域](results/fps_io_scratch.json) にある。静的な作業領域や無検査の読み込みで速度を上げる変更は行わない。

通常と ASan/UBSan の単体テストで、uint32 上限・不規則な空白・入力バッファをまたぐトークン・末尾直後の `PROT_NONE` を確認した。追加で別々の入力の並行読み込み、異常文字・上限超過・長いトークンの fast path 不採用、長い leading zero、先行・後続の出力順序、`/dev/full` の書き込みエラーを確認した。

```sh
python3 test/benchmark/fps_io_pipeline.py --baseline ce81108 --output io_pipeline.json
```
