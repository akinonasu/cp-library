# 多項式除算の入力と結果作成

2026-10-19（Asia/Tokyo）、基準版 `144ae32387675fa2a889ea3e8cd19b03ad5016bf` に対する追加高速化。被除数のコピーを省き、除算の戻り値を64要素ずつ作成する。公開 API、入力の保存、配列の整列・padding に関する前提は維持する。

## 参照と不足していた処理

最速参照は Division of Polynomials の [409561](https://judge.yosupo.jp/submission/409561) と Inv of Polynomials の [409589](https://judge.yosupo.jp/submission/409589)。SHA-256 はそれぞれ `fd06ec63bfe326a8f8c2b25292ecf38d77c4fd0114fbaa2565e4c667b8b4eeb1`、`274d6c6107676bf6043aa5984e4b5788617ae7c8ff0ae1f157b6b0954e895306`。全体時間の比較では原本を編集していない。

除算・Half-GCD の計算手順は既に移植していたが、`native_divide()` は被除数を作業用配列へコピー・正規化してから、反転・折り畳み・差を計算していた。また、API の戻り値には8要素ごとに `vector::insert()` していた。

最終版では被除数を `span<const Mint>` のまま保持する。SIMD 読み込み時に実在する8要素を `memcpy()` し、その場で Montgomery ワードを $[0,p)$ に正規化する。端数はスカラーで読む。通常ワード用の内部関数を型付き入力にも使えるようにし、raw `uint32_t` の長除算では従来の `std::copy()` を残した。除数は従来どおり所有領域へコピーする。被除数のコピーと `Arena::footprint(n)` ワードの作業領域が不要になる。

結果作成は除算・級数除算専用の `append_division_words()` を追加し、64要素ずつまとめる。残りは元の8要素版 `append_words()` を使う。逆元・GCD が使う `append_words()` は従来の8要素版を維持する。コピー先は生存中の `Mint` 配列で、`Mint` が trivially copyable であることを検査する。予約した vector の要素外へ直接書き込まない。

時間計算量 $O(n\log n)$、追加空間 $O(n)$ は同じ。被除数への最後の参照は出力先の確保・追加より前に完了するため、入力 vector 自体を出力先にした場合も、元の要素を保存して商・剰余を追加する従来の動作を維持する。raw span API の入力と出力を重ねない前提も変えていない。

## 計測条件

AMD EPYC 9V74 / Linux x86_64 / GCC 14.2.0、CPU 2固定。全版を `-std=c++23 -O2 -DEVAL -DONLINE_JUDGE -ftrivial-auto-var-init=zero -march=haswell` でビルドし、assert を有効にした。ビルド・検証は `/tmp/cp-fps-tuning.lock` の共有ロック、計時は排他ロックで実行した。

最終測定は seed 20261028。各入力・各版を1回予備実行してから、各反復の実行順をシャッフルし21回測定した。全体時間は起動・ファイル入力・API・ファイル出力・終了を含む wall time。表はmsの中央値。paired 差は同じ反復の「基準版−候補」の中央値で、二つの中央値の差とは異なる。勝数はその差が正の回数。

## 採用しなかった候補

- Half-GCD の直接計算の閾値8/16/24/32/48/64/96/128/192/256を、公式max_random入力3件で各21回比較した。現行64より安定した改善は得られず、変更しなかった。
- 逆元の正規化と戻り値作成を融合し、行列の係数と合成係数から直接 SIMD 出力する候補を試した。最初の測定には約0.1msのpaired改善があったが、独立再試行で安定しなかったため採用しなかった。`polynomial_gcd_blocked.hpp` の製品差分はない。

## 検証

- GCC14 の通常 `-Wall -Wextra -Werror` で、ヘッダー単体、除算・GCD の単体テストが成功した。除算の ASan/UBSan も成功した。
- GCC13.3.0 の通常 `-Wall -Wextra -Werror` でも、ヘッダー単体と除算テストが成功した。
- 公式 Division of Polynomials 全35件、Inv of Polynomials 全18件を `checker input actual answer` の順で照合した。計時中の全公式出力にも同じ checker を適用した。GCD と級数除算は基準版とのトークン列を照合した。
- 出力転送は0/8/64/128/512要素前後と65537要素、係数倍0/1/17/$R$/$R^2$を照合した。入力直後を `PROT_NONE`、入力を読み取り専用にした。
- 被除数は前後に読み取り禁止ページを置き、129〜4097要素、端数と2冪境界、正規化前の上限側の Montgomery ワードを検査した。商と剰余から入力を復元し、元の内部ワードも保存されることを確認した。
- 入力と出力 vector の共有は `a→q,b→r`、`a→r,b→q`、`q=r=a` を検査した。元の要素の内部ワードと追加順を照合し、同じ期待値テストが固定基準版でも成功した。

[最終検証](results/fps_division_round2/final_check.json) にコマンド・出力・ヘッダーの前後ハッシュと公式全件の結果を保存した。最終ヘッダーのSHA-256は `9295aeb26c2835e22b2b013404c7343c7c096c41a384ea26e8e6ff81d0f51037`、単体テストは `0d5a16e9f3c6022484d74c2fe85b25d90ee32dea9cf4020f114145f18447b355`。

## 逆元バイナリの確認

小幅な退行の原因候補を調べるため、同じ flags の基準版・最終候補を `nm` / `objdump` で読み取り比較した。relocation、局所分岐先の位置、整列用 nop を正規化すると、raw fold・subtract と Half-GCD の euclid・combine の命令列は一致した。extend・apply も命令数は同じで、差は helper の template 化による call 名だった。jump は1055→1047命令、5185→5146bytesへ微減し、一部の `std::copy` が memmove の直接呼び出しから copy helper の呼び出しへ変わった。

GNU `size` の text 集計は438632→453849bytes、ELF の `.text` セクションは373373→387741bytesとなった。Mint/raw の除算特殊化に伴う配置や命令キャッシュの影響も候補だが、測定から原因は断定しない。SIMD の消失や主要な積和の命令数増加は見つからなかった。[比較結果](results/fps_division_round2/assembly_review.json) と比較スクリプトを保存した。追加実装は行っていない。

## 原票と再現

[最終測定](results/fps_division_round2/final_raw.json) に全試行、実行順、コンパイルコマンド、CPU、入力・参照原本・依存ヘッダー・ドライバー・バイナリのSHA-256を保存した。診断途中の候補、すべての試行、元のハーネスとドライバーも [同じディレクトリ](results/fps_division_round2/) にある。`manifest.json` は保存ファイルのハッシュ一覧である。

Library Checker の生成元は `1814c4e5205517e368bb57a8d1127eb961cfeaae`。公式入力と参照原本を用意して、Linux 上で次のように再現できる。

```sh
python3 test/benchmark/results/fps_division_round2/replay_final.py \
  --repository "$PWD" --work /tmp/fps-division-round2-replay \
  --official-root /tmp/library-checker-problems --references /tmp/fps-reference
```

`--prepare-only` を加えると、基準 commit を Git archive から復元し、最終パッチを適用して、両版の174ヘッダー・ドライバー・級数除算の生成入力のハッシュだけを確認する。この復元は [実行済み](results/fps_division_round2/final_replay_preparation.json)。再現ハーネスによる全計時の再実行は行っていない。通常実行では記録した flags で再ビルド・検証し、21回の測定を再実行する。ディレクトリの変更はソース中のパスだけに反映し、flags、seed、測定手順は維持する。バイナリのハッシュや絶対時間はコンパイラ・パス・実行環境によって変わり得る。
