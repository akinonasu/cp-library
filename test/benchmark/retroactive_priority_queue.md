# Fully Retroactive Priority Queue

## 参考文献・比較対象

- Demaine, E. D., Iacono, J., & Langerman, S. (2007). [Retroactive Data Structures](https://erikdemaine.org/papers/Retroactive_TALG/paper.pdf). TALG 3(2), Article 13. 操作履歴を変更するモデルと、部分的 retroactive priority queue の橋による構成。
- Demaine et al. (2015). [Polylogarithmic Fully Retroactive Priority Queues via Hierarchical Checkpointing](https://erikdemaine.org/papers/FullyRetroactive_WADS2015/paper.pdf). 任意時点への問い合わせを扱う階層チェックポイントによる構成も調査しました。

今回の実装は線形空間のブロック要約を使う fully retroactive 版です。更新・問い合わせの計算量は `docs/retroactive_priority_queue.md` に記載しています。2026-10-16 の Library Checker 公式 API には対応する retroactive priority queue 問題がなかったため、独立した時系列シミュレーターとの比較で検証しています。

## ブロックの要約

全要素は優先度、同順位なら挿入時刻で並べます。ブロック単体を空のキューから処理し、残った挿入を `alive`、削除された挿入を `dead`、削除操作数を $$p$$ として保存します。ブロック単体で空キューへの削除が来た場合は、その操作数だけを記録します。

ブロック直前の候補キー以下の要素数を $$c$$、`alive`・`dead` 中の候補キー以下の個数をそれぞれ $$a$$・$$d$$ とすると、ブロック適用後の個数は

$$a+\max(c-(p-d),0)$$

です。対象キー以下の個数に着目すると、挿入は $$c\gets c+1$$、削除は $$c\gets\max(c-1,0)$$ になり、この形は合成に閉じています。

この個数が正になる最小のキーを、全挿入の値順 treap 上で二分探索します。問い合わせ時刻を含むブロックだけを部分的に要約し、それ以前は保存済みの要約を使います。値順 treap は履歴の操作ノードを直接参照し、削除ノードの領域を再利用します。乱数生成には既存の `SplitMix64` を使います。

### 逆向きの判定

最終個数が $$k$$ より大きいことを要求するとき、$$a>k$$ なら直ちに成立します。そうでなければ、直前のブロックへの要求は

$$c>k-a+p-d$$

です。末尾からこの条件を伝搬し、必要数がその時点のキュー全体の個数以上になれば直ちに不成立と判定します。前から全ブロックを処理する方式と比較します。

## 再現方法

```sh
python3 test/benchmark/retroactive_priority_queue_variants.py /tmp/retro-pq-variants
g++ -std=c++23 -O2 -DNDEBUG -I . -I /tmp/retro-pq-variants test/benchmark/retroactive_priority_queue.cpp -o /tmp/retro-pq-bench
/tmp/retro-pq-bench 100000 5000 5 > /tmp/retro-pq.csv
```

10万操作の初期履歴、5千回の履歴変更、その後5千回ずつの過去時点の `top`・`size` を測ります。乱数は `std::mt19937_64(5834509)`、値は64 bit整数です。変更は挿入・削除操作の追加・値の変更・操作の取り消しを等確率で選び、成功件数も記録します。拒否された変更を含みます。計測は入出力と入力生成を含みません。

- `growing`: 初期履歴は挿入だけ。
- `balanced`: 最初の4分の1が挿入で、その後は削除・挿入を交互に行う。
- `steady`: 最初の512回が挿入で、その後は削除・挿入を交互に行う。

ブロック幅64・128・256・512・1024、および幅256の前向き判定を比較します。実行順を入れ替えて5回測り、全候補のチェックサムを照合します。初期履歴2千操作以下では、ベンチマーク内でも独立した `multiset` による全履歴の再実行と照合します。

幅を大きくすると問い合わせに有利な一方、1回の履歴変更で要約し直す範囲が増えます。更新も多い場合のバランスとして256を既定にし、問い合わせ中心の場合は512・1024も選べるようにしています。`balanced` では幅1024の問い合わせが幅256の約半分の時間でした。

assert 有効でも全候補・全試行のチェックサムが一致しました。幅256の `top` は `growing` 146.72 ms、`balanced` 761.07 ms、`steady` 133.25 msでした。

## 検証

GCC・Clang の単体テスト、ASan・UBSan を実行しました。`test/unit/retroactive_priority_queue.cpp` では、独立した時系列シミュレーターと3万2千回のランダム変更、各変更後の複数時点の状態、7時刻・2種類の値を使う全16,384パターンを比較しています。ブロックの分割・結合、値の変更、無効な操作の拒否、min/max、重複優先度と挿入時刻による順序、非デフォルト構築型・状態付き比較、64 bit時刻の端点、コピー・ムーブ、一括構築、ノード再利用も確認しました。

検証したヘッダー・単体テストと手元のソースの一致を確認し、使用した測定用ブランチはローカル・リモートの両方から削除しています。
