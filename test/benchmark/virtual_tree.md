# Virtual Tree

`graph/virtual_tree.hpp` は、前処理済みの `LCA`・`HLD` を参照して補助木を構築します。頂点の重複・空入力に対応し、元の頂点番号、親の圧縮 ID、親までの辺数、指定頂点かどうかを返します。

## 実装

- DFS の位置と元の頂点番号を一度取り出してソートし、隣接する指定頂点の LCA を計算する。
- 深さでスタックを調整し、確定した部分木から出力する。LCA を追加した後の二回目のソートを省く。
- 構築途中は親の欄で未確定の兄弟をつなぎ、親の確定時に圧縮 ID と辺数を埋める。頂点番号から圧縮 ID への全頂点分の配列を用意しない。
- 圧縮 ID は子から親の順とし、隣接リストを作らずそのまま DP できる。
- 指定頂点、スタック、結果の容量を再利用する。再帰、クエリごとの全頂点走査、頂点ごとのメモリ確保を使わない。
- `build_sorted` は元の木の DFS 順で渡すと最初のソートも省略する。
- 構造体を `emplace_back` で直接構築し、一時オブジェクトのコピーを省く。集成体の括弧による初期化に未対応のコンパイラでは、通常の `push_back` に切り替える。

## 参考

補助木の構築については [ABC340 G 公式解説](https://atcoder.jp/contests/abc340/editorial/9249)、利用例は [ABC359 G 公式解説](https://atcoder.jp/contests/abc359/editorial/10259?lang=ja) を確認しました。前者の「指定頂点と DFS 順で隣接する頂点の LCA からなる集合」を使います。公式解説の二回ソートする方式と、本実装の一回ソートしてスタックで構築する方式を比較します。

Library Checker では補助木自体を出力する問題を確認できなかったため、関連する LCA の AC 一覧を時間順に取得しました。取得時刻・一覧・ソース SHA-256 は `results/virtual_tree_reference.json`、取得スクリプトは `virtual_tree_reference.py` に残しています。

| LCA の参考提出 | 取得時の時間 | 手法・比較 |
| --- | ---: | --- |
| [#278239](https://judge.yosupo.jp/submission/278239) | 24 ms | 先頭の AC。親番号が子番号より小さい入力を利用し、部分木サイズから DFS 位置を生成。64 要素ごとの prefix / suffix とブロックの sparse table で RMQ。独自 mmap 入力 |
| [#370969](https://judge.yosupo.jp/submission/370969) | 27 ms | 同様の DFS 位置生成と、64 要素単位の RMQ。ブロック間を disjoint sparse table で処理 |
| [#370928](https://judge.yosupo.jp/submission/370928) | 27 ms | 同様の DFS 位置生成と、ブロック間の sparse table による RMQ |

参考提出は LCA だけを求めるプログラムであり、補助木構築の速度比較には使っていません。本実装は任意の頂点番号・根を受け付ける既存の `LCA`・`HLD` を共有します。LCA 自体の RMQ の変更は行いません。参考の時間は Library Checker の入出力込みの時間で、下記の測定値とは別です。

## 測定条件

WSL2 / Linux x86_64、Intel Core i7-13700F、GCC 15.2.0。CPU 2 に固定し、1 回のウォームアップ後に各 7 回を測り、中央値を取ります。順序は固定 seed でシャッフルします。実行ファイルは Linux 側の `/tmp` に置き、他のテストやコンパイルとは同時実行しません。AtCoder 実機の測定ではありません。

- generic: `-std=c++2b -O2 -DNDEBUG`
- native: 上記に `-march=native -ftrivial-auto-var-init=zero` を追加

元の頂点数は 200,000。パス・星・二分木・ランダム木の頂点番号と辺の順序をシャッフルします。指定頂点は一様乱数で選び、重複を含みます。入力列長とクエリ数は `(2,300000)`、`(32,20000)`、`(1024,1000)`、`(100000,10)` です。

`virtual_tree.cpp` の比較元は、指定頂点のソート・重複除去、隣接 LCA の追加、二回目のソート・重複除去、祖先関係によるスタック構築を行います。指定フラグは整列済みの指定頂点列との線形走査で付け、全頂点分の初期化や二分探索は使いません。比較元も配列の容量を再利用し、本実装と同じ情報を返します。

構築ループと全結果のチェックサムを測り、最初のメモリ確保を含めます。木の前処理、入力生成、ソート済み方式へ渡す前のソート、入出力、最後のオブジェクト破棄は測定外です。HLD についても同じ一回ソートの構築法を測定します。全試行・全方式で、元の頂点、親の元の頂点、辺数、指定フラグから得たチェックサムを照合します。

環境、フラグ、seed、ソースのハッシュ、全試行の時間は `results/virtual_tree_generic/results.json`・`results/virtual_tree_native/results.json` に保存します。

## 構築方法の調整

最初の実装では構造体の一時オブジェクトを `push_back` していました。generic では速かった一方、native では遅くなるケースがあったため、同じ入力で直接構築する版と比較しました。`scalar` はさらにスタックからのコピーを各要素の読み取りに分けた版です。

| 形状・入力列長・クエリ数 | 一時オブジェクト | 直接構築 | scalar |
| --- | ---: | ---: | ---: |
| パス・32・20,000 | 75.088 | 24.737 | 24.207 |
| 星・32・20,000 | 58.556 | 26.423 | 25.794 |
| ランダム・1,024・1,000 | 115.889 | 79.430 | 78.945 |

上表は native の ms です。直接構築を採用しました。`scalar` の追加の差は小さかったため、スタックの取り出し方は維持しています。各候補の完全なヘッダーと全試行は `results/virtual_tree_tuning.json`、再測定用スクリプトは `virtual_tree_tuning.py`、変更前の全ケースは `results/virtual_tree_initial_generic/results.json`・`results/virtual_tree_initial_native/results.json` にあります。

[Apple の対応表](https://developer.apple.com/xcode/cpp/) では集成体の括弧による初期化は Xcode 16 以降なので、旧 Apple Clang 向けの分岐を追加しました。この分岐の追加は測定後ですが、GCC の前処理後のコードが測定版と一致することを確認しています。測定版と最終版のハッシュ・一致の記録は各結果の `compatibility_update` と `results/virtual_tree_compatibility.json` に残しています。旧コンパイラ向けの分岐も強制して ASan/UBSan で確認しています。

## 検証

- 小さい木の全部分集合、ランダム木・頂点番号・根・入力順・重複を含む集合について、全対の素朴な LCA から求めた頂点集合と最も近い祖先を照合。
- 圧縮後の全対 LCA、辺数、指定フラグ、子から親の順序、補助木 DP による指定頂点間の距離和を照合。
- `LCA`・`HLD`、通常・ソート済み構築、空入力、コピー、再構築を確認。LCA に追加した `subtree` の DFS 区間も素朴な祖先判定と照合。
- 300,000 頂点のパス・星・二分木を全頂点指定で構築し、それぞれ 30,000 回の小さいクエリも実行。
- GCC 13・15、Clang、release の `-DNDEBUG -Werror`、ASan/UBSan、ヘッダー単独・結合コンパイルを確認。
- Library Checker の LCA 公式 25 ケースを、既存 LCA と補助木の根を返す新規プログラムで GCC・Clang の両方で確認。これは補助木の辺全体の検証を代替しないため、上記の独立した照合も行う。
- 公開関数の表とページ生成を確認。
