# FPS の一点評価

2026-10-19（Asia/Tokyo）に `fps::eval(x)` の直列 Horner 法を調べた。一点評価に独立した Library Checker の問題はないため、直列の Horner 法を比較元にして、同じ入力・評価点で計算部分を測定した。

32 項以上を指数の余りごとに分ける。scalar では 4 本と 8 本、AVX2 では 8 lane の漸化式を 1・2・4 本持つ構成を比較した。固定した `x^8` または `x^32` に対する Shoup 乗算を使い、最後に各組を Horner 法で結合する。32..63 項は SIMD 1 本、64 項以上は SIMD 4 本を採用した。AVX2 を使えない環境では scalar 8 本、短い入力は直列に戻す。入力の保存と公開 API を維持する。

## 測定

AMD EPYC 9V74、GCC 14.2.0、Linux x86_64、CPU 2 固定。`-std=c++23 -O2 -DEVAL -DONLINE_JUDGE -ftrivial-auto-var-init=zero -march=haswell`、assert 有効。入力は seed 20261019 で生成し、同じ入力に対して評価点を 17 から順に変える。1 回の測定内では `min(4096,max(8,1000000/n))` 回評価し、入力生成とチェックサムを計時から除く。各候補の計算は `noinline` の関数ポインタ経由で呼び出す。

全版のビルドを終えてから排他ロックで測定し、他のコンパイル・検証を並行実行しない。各版 1 回予備実行後、順序をシャッフルして 9 回測定する。全試行のチェックサムを照合する。以下は 1 回の評価の中央値、単位 ms。


## 検証と他の線形演算

`test/unit/fps_horner.cpp` で、0..129 の SIMD 境界と 1023..1025、32769 項、評価点 0・1・-1・2・-2・ランダム値、Montgomery ワードの上限側、入力の保存を確認した。素朴な Horner 法と内部関数・公開 `eval()`・portable な scalar 8 本の値を照合する。通常の `-Wall -Wextra -Werror` と ASan/UBSan を通過した。LeakSanitizer は既存の ptrace 制約により `detect_leaks=0` とした。

`onemul(d,c)`・`onediv(d,c)` は明示的な AVX2 経路を持たず、`Mint` の演算とコンパイラ最適化に依存するループである。前者は後方更新、後者は前方の係数に依存する更新なので、ループの向きは維持する。今回は変更していない。

`diff()` は `NTT::weighted`、`integral()` は `NTT::product` を使い、どちらも既存の AVX2 経路を持つ。返り値の長さは入力と同じという既存 API を維持している。
