# Shortest Path 追加測定 4

[前回](shortest_path_round3.md)の `max_sparse_random_01` の約 9.7% の悪化を調べます。比較対象は `bd29f70`、前回より前の版は `f4aa743` です。

## 再現と原因の切り分け

前回は各 7 回の中央値で、実提出の全体時間が 15.39 → 16.88 ms でした。一方、同じ run の区間ドライバでは入力・構築・探索がいずれも改善していました。全試行を確認すると、CSR 構築が約 3 ms と 6 ms の二群に分かれ、遅い群の割合によって中央値が逆転していました。

依存ヘッダーを各 Git revision から凍結し、実提出と区間ドライバを別々に再測定しました。全体時間は fresh process、CPU 2 固定、各試行で実行順を変え、共有 lock `/tmp/cp-wm-opt.lock` の下で計測します。入力・バイナリ・出力は Linux `/tmp` に置きます。

15 回の実提出の中央値は `f4aa743` 14.08 ms、`bd29f70` 13.84 ms でした。追加の 41 回でも 14.60 → 13.97 ms で、固定的な退行は再現しませんでした。前回の 9.7% をライブラリの変更に起因する退行とは断定できません。

診断用ドライバで構築を分けると、prefix sum は約 0.05–0.06 ms、Arc の確保・初期化は約 0.78–0.94 ms でした。揺れは `arcs_[--offset_[from]]` へ辺を配置する scatter にあり、約 2.0 ms と 5.1 ms に分かれます。scatter 中の minor / major fault は 0、Arc の初期化時の minor fault は 977 で一定でした。配列の相対アドレスも一定で、ページフォルト数の増加や ASLR による相対配置の変化では説明できません。

変動する区間は特定できましたが、ホストのキャッシュ・CPU・メモリ状態のどれが変動の根本原因かは断定していません。診断版は計時や資源取得を追加しているため、実提出の正式速度とは区別します。全試行・条件・診断変更は [診断記録](results/shortest_path_round4_diagnosis) に残します。

## 比較した変更

一般の CSR 構築では出辺数の累積値から書き込み先を決めます。入力順がランダムな疎グラフでは、次数配列と Arc へのランダムアクセスが生じます。後で処理する辺の書き込み先を先読みし、キャッシュミスの待ち時間を減らす方法を比較しました。

候補・全試行・ソース差分は [候補の記録](results/shortest_path_round4_variants/codegen/README.md) に残します。基準は `bd29f70` です。noinline 属性による分離、旧キューへの差し戻し、入次数判定の後回し、Arc の早期確保・初期化、32 bit offsets と従来幅への fallback も比較しました。

最初は、頂点数が 8192 以上なら先読みを行い、入次数判定を入力後に移す候補 A を全 36 ケース・各 21 回で比較しました。疎グラフは改善しましたが、`max_star_00` が native で 9.145 → 9.740 ms、generic で 9.381 → 9.810 ms と悪化しました。構築区間にも同じ悪化があり、全体時間の揺れだけでは片付けられません。[候補 A の全結果](results/shortest_path_round4_variants/candidate_a/README.md)を残し、この候補の採用は見送りました。

`max_star_00` は頂点数が 500000 あっても、出辺を持つ頂点は 32 個です。多くの頂点からランダムに配置する疎グラフと比べると、繰り返しアクセスする行が少なく、先読みの固定費が構築時間の増加につながると考えられます。そこで頂点の総数から、出辺を持つ行の数へ適用条件を変えました。入次数判定も入力中に行う従来の方式を残し、CSR の配置だけを変更する候補に絞りました。

[適用条件と入次数判定の比較](results/shortest_path_round4_variants/active/README.md)は、代表 7 ケース・各 9 回の予備測定です。出辺を持つ行数で先読みを選び、入力中の入次数判定を保つ `original_active` を最終候補としました。先読みを使わない版や入次数判定だけを後回しにする版も比較し、追加の辺走査を避けて既存実装との差を小さくしています。

最終的に採用したのは次の変更です。

- 通常の CSR 配置で、32 辺先の次数と書き込み先 Arc を先読みします。末尾 32 辺は従来の配置です。
- 出辺を持つ行が 8192 個未満なら先読みを省きます。行数は既存の累積和を計算する際に数えるため、追加の配列や独立した全頂点走査は不要です。小さい密グラフや出辺が少数の頂点に集中する場合を避ける性能上の目安で、普遍的なキャッシュ境界とはみなしません。

先読みの診断比較では、同じ run の 41 回で実提出の全体が 13.62 → 12.77 ms、scatter の中央値が約 2.05 → 1.20 ms でした。この診断は適用条件を絞る前の先読み候補の比較です。初期化時の fault 数は変わりません。

先読みする辺はまだ配置されていないため、その始点の残りの辺数は 1 以上です。したがって `offset_[from]-1` は Arc 配列内に収まります。計算結果は先読みの成否に依存しません。GCC・Clang で先読みを使い、それ以外では従来の配置を使います。数値型・辺数・入力順・公開 API を制限せず、既存の一本道と一意経路の処理も残します。

先読み距離 8・32・64 を比較し、代表ケースでバランスのよい 32 を選びました。入力を計時外にした CSR 単体の測定でも、頂点数 512–65536、平均出次数 2・16 で切替を比較しました。小さい疎グラフでは先読みが逆効果になり、次数によって境界も変わります。32 bit offsets は一部で改善しましたが、幅の切替と探索コードの複製が必要で、先読みだけより疎グラフの改善が小さかったため見送りました。noinline・旧キュー・早期確保にも採用の根拠が得られませんでした。

参考提出 [407097](https://judge.yosupo.jp/submission/407097)・[404592](https://judge.yosupo.jp/submission/404592) の公式順位とソース hash は前回と同じでした。[取得記録](results/shortest_path_round4_reference.json)に保存しています。参照は専用の入力処理や 32 bit offsets などを使い、辺順の契約も異なります。第三者のソースは ignored cache のみに置きます。

## 正式測定

WSL2 / Linux x86_64、Core i7-13700F、GCC 15.2 です。共通フラグは `-std=gnu++23 -O2 -DNDEBUG -DATCODER -DONLINE_JUDGE -ftrivial-auto-var-init=zero`、native は `-march=native` を追加します。公式 29 ケースと seed `20261019` の合成 7 ケースを使います。実提出の全体時間には入力・構築・探索・出力・プロセス起動終了を含みます。

```sh
python3 test/benchmark/shortest_path_round4.py \
  --output test/benchmark/results/shortest_path_round4_final_native \
  --trials 21 --native --submissions \
  --reference fastest_407097=.verify-helper/cache/shortest-path/reference/407097.cpp \
  --reference reference_404592=.verify-helper/cache/shortest-path/reference/404592.cpp
```

`--native` を外すと generic 設定です。generic の正式 run は参照提出の `--reference` も外し、出力先を `shortest_path_round4_final_generic` に変えます。各ケース 1 回 warmup 後に測り、全試行の距離と warmup の経路を確認します。`baseline` / `current` は区間ドライバ、`own_baseline` / `own_path` は計時を挿入しない実提出です。区間ドライバの全体時間を実提出の速度として扱いません。

## 検証

両設定の全 36 ケース・各 21 回で距離を照合し、warmup の経路を公式 checker または合成データの辺で検証しました。実行終了時にライブソース・凍結ソースの hash が変わっていないことも確認しています。

[最終版の検証記録](results/shortest_path_round4_validation.json)には GCC・Clang の unit 12 件、ASan / UBSan 7 件、公式 checker 174 件を保存しました。CSR の境界・同じ行への集中・辺順・汎用の重み型・再構築・例外と Dijkstra の推移的な依存先を対象にしています。[ドキュメントの検証](results/shortest_path_round4_docs.log)も成功しました。候補 A の検証は [初回候補の記録](results/shortest_path_round4_variants/initial_validation)へ分けて保存しています。
