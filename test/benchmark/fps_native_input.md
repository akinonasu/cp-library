# FPS 対数の入力コピーと最上段変換の融合

2026-10-18 UTC に、公開 Mint 配列から対数計算用の内部配列へのコピーを削減した。`native_log` の出力次数が 262,144 以上の場合だけ採用した。冪にも同じ変更を試したが、一貫した改善がなく不採用とした。

基準は `4765ceb5f995801d27b23840392c9c354ecdecb9`。その後の `520e972` は FPS 関連ファイルを変更していない。比較した原本は [log_of_formal_power_series / 409452](https://judge.yosupo.jp/submission/409452) と [pow_of_formal_power_series / 409718](https://judge.yosupo.jp/submission/409718)。原本ソースと SHA-256、各候補の差分、全試行の原票を [results/fps_native_input/](results/fps_native_input/) に保存した。

## 採用した変更

従来は出力に必要な入力全体を `[0,p)` に正規化して内部配列へコピーし、その配列を最上段変換と微分で再読込した。採用版は初期逆数に必要な先頭 `min(input,n,log_block(n))` 項だけコピーする。残る変換と微分は公開 `const Mint` 配列から直接読み、正規化を演算に融合する。

完全な 8 係数は `memcpy`、末尾は範囲内の係数だけを局所配列へコピーして読む。入力を変更せず、追加のアラインメント・padding を要求しない。既存の `Source` と `Transform` の呼出形式を保ち、最上段処理と対数微分の本体をテンプレートで共有した。公開 API、汎用型、Clang・他アーキテクチャの経路は変更していない。

最初の候補は小さい次数にも適用したが、131,073 項で退行した。作業配列の削減によって約 2 MiB の確保境界を下回り、既存 `Arena` の大きいページを使う経路から外れるためだった。旧配置を保つ候補も比較した結果、262,144 項未満は従来経路を維持することにした。500,000 項では係数コピー領域を約 1.5 MiB 削減する。

## 対数の測定

AMD EPYC 9V74、Linux x86_64、GCC 14.2.0、CPU 2 固定。オプションは `-std=c++23 -O2 -DEVAL -DONLINE_JUDGE -ftrivial-auto-var-init=zero -march=haswell`、assert は有効。ビルドと検証は `/tmp/cp-fps-tuning.lock` の共有ロック、計時は排他ロックを取った。各行は予備実行 1 回の後、seed `20261019` で順序を入れ替えた 21 回の中央値である。

kernel は公開 `fps::log` の呼出を測り、作業領域と出力の確保を含む。入力生成と結果のハッシュ計算は含めない。whole はファイル入出力とプロセス起動・終了を含む。境界入力は公式 `max_random_00` の係数を切り出して作り、変更していない原本 409452 の出力を公式 checker の答えとした。

| 項数 | kernel 基準 | kernel 採用版 | whole 基準 | whole 採用版 |
| --- | ---: | ---: | ---: | ---: |
| 131,073 | 2.018089 ms | 2.042475 ms | — | — |
| 262,144 | 4.257868 ms | 4.157789 ms | 7.739139 ms | 7.545100 ms |
| 262,145 | 4.201684 ms | 4.111479 ms | 7.940129 ms | 7.736355 ms |
| 393,217 | 6.640500 ms | 6.559790 ms | 11.578193 ms | 11.350543 ms |
| 500,000 | 8.846398 ms | 8.714412 ms | 14.392929 ms | 14.207342 ms |
| 524,288 | 8.840781 ms | 8.694432 ms | — | — |

131,073 項は両版で従来経路を使い、中央値の小差はコード配置等も含む測定の揺れである。500,000 項の whole は同じバイナリを seed `20261020` で順序を入れ替えて 99 回ずつ追加測定し、15.437993 ms → 15.336993 ms だった。大次数の kernel では約 0.1〜0.15 ms の改善が見られたが、whole の揺れは大きく、改善幅を過大に解釈しない。

原本との比較は最初の候補を測った別セッションに含む。公式 `max_random_00` は基準 15.681659 ms、初期候補 15.395631 ms、原本 13.882757 ms。`max_random_01` は 14.649149 / 14.333569 / 13.029314 ms だった。採用版の測定と直接つなげた速度差は算出しない。この追加変更だけで原本と同速になったとは言えない。

## 冪の不採用候補

冪も対数微分を使うので、公開入力からの直接読込を試した。初期逆数が prefix の読込を終えてから結果領域を再利用し、変換済みの値を受け取る observer の順序・領域を維持した。

| 対象 | 基準 | 候補 | 原本 409718 |
| --- | ---: | ---: | ---: |
| kernel 262,144 項 | 8.928262 ms | 8.878779 ms | 8.661574 ms |
| kernel 262,145 項 | 12.304396 ms | 12.188103 ms | 12.110778 ms |
| kernel 393,217 項 | 16.966188 ms | 17.006298 ms | 16.587233 ms |
| kernel 500,000 項 | 18.696467 ms | 18.733593 ms | 18.309691 ms |
| whole max_random_00 | 25.020917 ms | 24.917253 ms | 22.909329 ms |
| whole max_random_01 | 25.179054 ms | 25.132234 ms | 23.141825 ms |

各 21 回の中央値。kernel は乱数 seed `20261019`、定数項 1、指数 $$10^{18}$$。差は試行のばらつきに比べて小さく、大次数の kernel は改善していないため採用しなかった。指数・冪用ヘッダーは変更していない。

## 検証と再現

対数は既存の `f * log(f)' = f'` の検査へ 262,143 / 262,144 / 262,145 / 393,217 項を追加した。短い入力・出力より長い入力・`2p` 直前の内部表現・入力保持を検査した。さらに読取専用 Mint 配列の末尾を `PROT_NONE` ページに接して置き、padding のない入力で両 integrate モード・長さ・値の関係・入力保持を確認した。通常実行と ASan/UBSan で検証し、計時した whole の全出力は公式 checker を通過した。

冪候補は既存の指数・冪テスト、汎用 FPS テスト、ASan/UBSan、読取専用 guard page の短い入力から 500,000 項までの検査、公式 37 入力を通過した。独立したコードレビューでも prefix の寿命、observer の順序、入力境界の問題は見つからなかった。

`log/` の `results.json` は初期候補、`layout.json` は配置比較、`shared.json` は採用版、`repeat.json` は採用版の追加 99 回の原票。`pow/` は不採用版の原票・差分・検証資料。基準コードと候補を別ディレクトリに復元し、記録したヘッダーハッシュと照合できる。

```sh
python3 test/benchmark/results/fps_native_input/log/prepare.py \
  "$PWD" /tmp/fps-log-native-reproduction
python3 test/benchmark/results/fps_native_input/pow/prepare.py \
  "$PWD" /tmp/fps-pow-native-reproduction
```

公式問題の使用コミットは `1814c4e5205517e368bb57a8d1127eb961cfeaae`。問題生成、ビルド、checker、各測定の実行順序は [log/README.txt](results/fps_native_input/log/README.txt) と [pow/README.txt](results/fps_native_input/pow/README.txt) に記載した。元の測定スクリプトはそのまま保存し、`prepare.py` がパスだけ置き換えた `_local.py` を作る。再測定結果は復元先へ出力し、保存した原票を上書きしない。
